# v1.1.14 per-account autologin — EOD handoff (2026-05-18)

End-of-day handoff continuing the morning's work. Same branch, same beta tester, but the scope and approach have shifted meaningfully based on today's findings on Windows.

## TL;DR

**Goal restated:** Per-account credentials for every AxiAM-launched GW2 instance, including concurrent multi-instance. User explicitly said: "I care most that it saves the credentials per account. Clicking the launch button is fine as long as AxiAM handles the user's credentials through the local.dat."

**Verified today on a real Windows install:**

1. **`-autologin` does NOT auto-submit on current GW2 clients.** Verified by spawning `Gw2-64.exe -autologin` bare (no AxiAM). Saved credentials pre-fill the email/password fields but the user still has to click Login. Same on m0mentkill3r's box and darkharasho's. This invalidates the morning's framing of "the bug" — we were never going to skip the login screen. The actual deliverable is "each account's login screen pre-fills with that account's email/password" — which take-2 already does for single-instance.
2. **Take-2 (Local.dat install-to-host) works for single-instance.** Each account's launch installs that account's saved `Local.dat`, GW2 opens with that account's creds pre-filled, user clicks Login.
3. **Concurrent multi-instance with per-account creds is structurally hard.** GW2's launcher does not tolerate isolated appdata across concurrent instances — the second instance hits "Download failed (5)" during its update check, even with `-shareArchive` and a 20-second pre-spawn dwell.
4. **Take-3 (NTFS junction on `%APPDATA%\Guild Wars 2\`) implemented and committed behind a feature flag, but does not solve concurrent multi-instance.** Single-instance works under junction; concurrent fails for the same launcher reason. Flag is rolled back to `false`.

**Decided next step:** **DLL injection / file-path hooking, the Gw2Launcher pattern.** Hook `NtCreateFile` (or `SHGetFolderPath`) inside each `Gw2-64.exe` process so it transparently reads/writes a per-account `Local.dat` while everything else in appdata stays shared. The launcher sees the appdata it expects; only the credential file is redirected.

## Today's wins (shipped, default-on)

These survive regardless of which multi-instance strategy we go with.

### 1. Cross-platform test fixes (`d49c130`)

- `electron/localDat.test.ts` — `snapshotHostToAccount` tests now use `path.normalize('/host')` so the `startsWith` predicate matches whichever separator the host produces. Fixes 3 spurious failures on Windows.
- `electron/mutexCloser.test.ts` — `resolveProtonContext` describe block guarded with `describe.skipIf(process.platform === 'win32')`. That code path only runs on Linux; the tests pinned POSIX paths that `path.join` mangled on Windows.

### 2. Cross-contamination prevention (`284d2f3`)

The quit handler used to snapshot host → profile on any quit, even for fresh accounts that quit before logging in. That captured the *previous* account's credentials (still at host) as if they were this account's. Bug actively poisoned Alt's snapshot during morning testing.

Fix:
- `electron/main.ts` now tracks `launchContexts: Map<accountId, { installed, startedAtMs }>` — installed=true means snapshot was installed at launch (host had this account's data), installed=false means a fresh launch (host has whatever was there).
- On quit: if `installed=false` AND elapsed < 15s, skip the snapshot. Logs `[snapshot] account=… skipped: fresh-account quit after Xms (<15000ms threshold) — likely no authentication happened`.
- Real-world verified: launching fresh Alt while Main's data was on host, then clicking Stop → Alt's profile stayed empty, no cross-contamination. Then logging in as Alt for >15s → snapshot correctly fires.

### 3. Stop-phase re-launch fix (`284d2f3`)

The `launch-account` IPC handler checked state *before* setting it. A stale 'stopped' phase from a prior session would cancel every future Launch click with `[serializer] skipped: launch was cancelled while queued (phase=stopped)`.

Fix: set `launch_requested` *before* the serializer wait, so the cancellation check only triggers on Stop clicks that happened *during* the queue wait. Verified — clicking Launch after Stop now proceeds normally.

### 4. Always pass `-shareArchive` (`9be6acc`)

Was only included when the user had it in their per-account `launchArguments`. Existing accounts created before take-2 have empty `launchArguments` and hit "Unable To Open Archive File" on a second concurrent instance. Now AxiAM auto-injects `-shareArchive` into spawn args (unless the user already supplied it).

## Open work — DLL injection (take-4)

The pivot. Replaces both take-2 and take-3 for the credential-file part.

**The concept (Gw2Launcher's approach):**
- Compile a small Windows DLL in C++ that hooks file-system APIs inside the target process.
- The DLL inspects each file-open call. If the path is `%APPDATA%\Guild Wars 2\Local.dat`, rewrite it to `<per-account-profile-dir>\Local.dat` before passing through.
- Inject the DLL into each `Gw2-64.exe` process at spawn time (CreateRemoteThread + LoadLibrary, or `CREATE_SUSPENDED` + bootstrap shellcode).
- Each instance now reads/writes its own `Local.dat` while sharing all other appdata files (so the launcher's update check still works).

**Why this fixes everything:**
- No appdata isolation → GW2's launcher sees the shared state it expects → no "Download failed (5)".
- Per-process Local.dat redirection → no file lock contention → concurrent multi-instance works.
- The hook can target the specific account ID at injection time (the DLL gets the target path as a parameter), so each spawn's DLL knows which file to redirect to.

**What we already have to lean on:**
- `tools/mutex-closer/` already ships a C++ helper exe with a CMake/MSVC build. We can model the DLL build off it.
- `electron/mutexCloser.ts` already has a `spawn`-based interface for invoking native helpers; the injection orchestrator can follow the same pattern.

**Risks / unknowns:**
- DLL injection can trigger AV/EDR alerts. AxiAM may need to be signed and the DLL needs to look benign. Worth checking with m0mentkill3r whether his AV flags any of our existing native binaries.

- 32-bit vs 64-bit: `Gw2-64.exe` is 64-bit; the DLL must match.
