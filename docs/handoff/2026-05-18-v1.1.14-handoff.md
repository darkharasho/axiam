**Known issue surfaced in his beta.2 log:**
On a second concurrent launch, `installSnapshotToHost` retry exhausts with `EBUSY` because **the first running `Gw2-64.exe` keeps `Local.dat` open with an exclusive write lock for the whole session**, not just briefly at startup as our design assumed. Result: second account spawns *without* `-autologin` and the user has to type credentials. The multi-instance autologin path is broken for v1.1.14-take-2 as currently implemented.

## Architecture of take-2 (the Gw2Launcher pattern)

Spec: `docs/superpowers/specs/2026-05-17-per-account-autologin-host-install-design.md`
Plan: `docs/superpowers/plans/2026-05-18-per-account-autologin-host-install.md`

**Per-account snapshot storage:** `userData/profiles/<accountId>/Guild Wars 2/Local.dat` (unchanged from take-1's storage layout).

**Per-launch sequence** (Windows only; Linux untouched):

1. `launchSerializer.acquire()` — FIFO queue, one launch at a time
2. Cancellation check: bail if state machine moved to `stopping`/`stopped` while queued
3. Existing multi-instance gate + mutex-close
4. `installSnapshotToHost(accountId)` copies the account's `Local.dat` over the host file. Retry with backoff for 3 s on `EBUSY`/`EACCES`/`EPERM`. If retry exhausts, drop `-autologin` from args.
5. Spawn `Gw2-64.exe` with `-autologin` (if install succeeded) and `-mumble`.
6. `waitForAccountProcess` + `manualAccountPidBindings` (existing detection)
7. `quitWatcher.noteLaunch(accountId, pid)` — track the bound PID
8. **4 s dwell** — let GW2 read `Local.dat` before the next install can overwrite
9. Release serializer slot

**Quit detection + auto-snapshot-back:**

- `quitWatcher` polls `Gw2-64.exe` PIDs every 2 s
- When a tracked PID disappears AND **no other GW2 is running**, copy host `Local.dat` back into the account's profile dir (preserves graphics/UI settings for single-instance use)
- If another GW2 is still running, skip the copy-back (cross-contamination guard — the host file is mid-write by the other process)
- Explicit Stop drops the binding silently without firing the snapshot

**New files:**
- `electron/launchSerializer.ts` — async FIFO mutex
- `electron/launchSerializer.test.ts`
- `electron/quitWatcher.ts` — PID-poll EventEmitter
- `electron/quitWatcher.test.ts`

**Modified:**
- `electron/localDat.ts` — adds `installSnapshotToHost`, `snapshotHostToAccount`, internal `getHostLocalDatPath`; removes the dead `getAccountAppDataDir` from take-1
- `electron/localDat.test.ts` — adds copy-function tests (uses `vi.mock('electron', …)` to fake `app.getPath`)
- `electron/main.ts` — launch handler rewrites described above; quitWatcher lifecycle wiring; constant additions

## History recap

v1.1.10–v1.1.12 fixed the original `-shareArchive`/multi-instance bugs for m0mentkill3r:
- v1.1.10: Linux launcher polish (mostly irrelevant to him)
- v1.1.11: Windows auto-locates `Gw2-64.exe`; direct-exe launch bypasses Steam's single-instance gate
- v1.1.12: Mutex-closer ships (closes `AN-Mutex-Window-Guild Wars 2` so a second `Gw2-64.exe` can start)
- v1.1.13: Catch `EBUSY` from `restoreLocalDat`'s `fs.copyFileSync` so a locked Local.dat doesn't silently abort the second-instance launch

After v1.1.13 he had **two `Gw2-64.exe` processes running side-by-side** but only the first had autologin. That's the remaining bug.

**v1.1.14-take-1** (merged to `main`, beta.1 prerelease): tried to give each account its own `%APPDATA%\Guild Wars 2\` directory by spawning `Gw2-64.exe` with `APPDATA` env var pointing at `userData/profiles/<accountId>`. Beta test on 2026-05-18 confirmed GW2 honors the env var for *some* writes but resolves credential read/write via `SHGetFolderPath(CSIDL_APPDATA)` (registry-backed), so the per-account files got created but autologin never picked them up. Approach abandoned.

**v1.1.14-take-2** (this branch): Gw2Launcher pattern. Implementation complete; testing in progress.

## What we likely need to figure out next

Depends on m0mentkill3r's "does single-instance autologin actually work?" answer:

**If yes (single-instance autologin works):**
- Multi-instance autologin still broken by the `EBUSY` lock issue (his log line 44).
- Options:
  - A. Accept "first instance autologins, subsequent ones type manually" as the take-2 ship state. Document the limitation. Cut v1.1.14 final.
  - B. Find a way to install Local.dat without needing exclusive write access (e.g., terminate GW2's file handle on it before our copy — but that's risky and might mid-write corrupt the file).
  - C. Pre-position all per-account Local.dats up front somehow (probably not viable since the host path is one file).
  - D. Different mechanism entirely for multi-instance (per-account directory junctions? per-account Windows user profiles? both are bigger projects).

**If no (single-instance autologin doesn't work):**
- GW2 has likely moved credentials out of `Local.dat` entirely on his client version. Possible storage: Windows Credential Manager, DPAPI-encrypted registry, or a separate file we don't know about.
- Need to figure out what GW2 actually does on his machine. Compare with a working Gw2Launcher setup on the same machine if he has one (Gw2Launcher uses the same Local.dat install pattern, so if it works there but not here, something else is different).
- The screenshot already shows `Local.dat` mtime is from yesterday despite his test launches today, which strongly suggests GW2 isn't writing it for credential persistence on his setup.

## Beta release process (so you can ship v1.1.14-beta.3+ from Windows)

```bash
# 1. Temporarily bump version (don't commit):
node -e "const fs=require('fs'); const p=JSON.parse(fs.readFileSync('./package.json')); p.version='1.1.14-beta.3'; fs.writeFileSync('./package.json', JSON.stringify(p,null,2)+'\n');"

# 2. Build Windows installer with --publish=never so electron-builder doesn't upload:
npm run build:electron
npm run build
npx electron-builder --win --publish=never

# 3. Verify the artifact:
ls -lh "dist_out/AxiAM Setup 1.1.14-beta.3.exe"   # expect ~77 MB

# 4. Restore package.json:
git checkout package.json

# 5. Create the prerelease and upload (requires gh CLI authenticated):
gh release create v1.1.14-beta.3 \
  --prerelease \
  --title "v1.1.14-beta.3 — <short description>" \
  --notes "<what changed since beta.2>" \
  "dist_out/AxiAM Setup 1.1.14-beta.3.exe"

# 6. The URL to share:
#    https://github.com/darkharasho/axiam/releases/tag/v1.1.14-beta.3
```

**Why a prerelease, not a real release:** auto-updater config (`releaseType: 'release'` in package.json's electron-builder block) ignores prereleases, so existing users won't be auto-pushed to a half-tested build. Only people who manually download from the prerelease page get it.
